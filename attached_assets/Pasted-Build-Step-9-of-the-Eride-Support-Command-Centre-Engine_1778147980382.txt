Goal:
Build the engineering escalation layer so support/admin can prepare a technical ticket for developers and link it to Linear manually.

Important:
Do not add actual Linear API integration yet.
Do not add Sentry integration yet.
Do not add GitHub integration yet.
Do not add automatic Replit execution.
This step is only manual Linear handoff, Linear link storage, and structured developer/Replit prompt generation.

Database:

Create support_ticket_linear_links table:
- id
- supportTicketId
- linearIssueId nullable
- linearIssueKey nullable
- linearIssueUrl nullable
- linearTeamKey nullable
- linearStatus nullable
- createdByName nullable
- createdAt
- updatedAt
- lastSyncedAt nullable

Relationship:
- linear link belongs to support ticket
- cascade delete if support ticket is deleted

Backend endpoints:

1. GET /api/support/tickets/:id/linear-link

Purpose:
Return the Linear link record for a ticket if it exists.

Must:
- verify ticket belongs to active Eride Technologies organisation

2. POST /api/support/tickets/:id/linear-link

Purpose:
Create or update the manually linked Linear issue details.

Input:
- linearIssueId optional
- linearIssueKey required
- linearIssueUrl optional
- linearTeamKey optional
- linearStatus optional
- createdByName optional

Validation:
- ticket must belong to active Eride Technologies organisation
- linearIssueKey cannot be empty
- if linearIssueUrl is provided, validate it is a URL
- upsert behavior: one Linear link per support ticket for now

3. DELETE /api/support/tickets/:id/linear-link

Purpose:
Remove an incorrect Linear link.

Must:
- verify ticket belongs to Eride organisation

Frontend:

Update /admin/support/tickets/:id

Add a new card:
Engineering Escalation

Place it near the workflow actions and developer handoff area.

The card must include:

A. Escalation readiness summary

Show:
- Ticket reference
- Product
- Priority
- Severity
- Category
- Current internal status
- Whether ticket has attachments
- Whether ticket has internal notes
- Whether ticket has a Linear link

Add visual indication:
- Ready for engineering if category is technical_bug, payment_issue, otp_verification_issue, document_upload_issue, performance_issue, system_downtime, or security_privacy_concern
- Otherwise show: “This may be a support-only ticket. Escalate only if technical work is required.”

B. Generate Linear Issue button

When clicked, generate copy-ready Linear issue text.

Linear issue title format:
[Priority] [ProductCode] [Category] — [Issue Summary]

Example:
[High] [EMA] OTP Verification Issue — WhatsApp OTP not sending

Linear issue body format:

SUPPORT TICKET ESCALATION

Support Ticket:
{{ticketReference}}

Product:
{{productName}} ({{productCode}})

Priority:
{{priority}}

Severity:
{{severity}}

Category:
{{category}}

Reporter Type:
{{reporterType}}

Environment:
{{environment}}

Page / Step:
{{pageOrStep}}

Application Reference:
{{applicationReference}}

Account Reference:
{{accountReference}}

Issue Summary:
{{issueSummary}}

What the user was trying to do:
{{whatWereYouTryingToDo}}

What went wrong:
{{whatWentWrong}}

Attachments:
{{attachment summary or “No attachments uploaded”}}

Current Support Status:
Public: {{publicStatus}}
Internal: {{internalStatus}}

Expected Engineering Action:
1. Reproduce the issue.
2. Identify the root cause.
3. Fix the issue.
4. Add or update a regression test.
5. Submit for review.
6. Return to support/QA for production verification.

Compliance Notes:
- Do not expose PII in logs, console output, Sentry, or Linear beyond what is necessary.
- Do not expose internal notes publicly.
- Do not use legal-decision language such as approved, rejected, or guaranteed.
- Preserve existing database IDs unless a schema change is explicitly required.
- The fixer cannot verify their own work.
- QA/support must verify on production before the user is told the issue is fixed.

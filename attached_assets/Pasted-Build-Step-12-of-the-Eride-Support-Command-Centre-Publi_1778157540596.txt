Goal:
Create a public ticket tracking experience so users can check the status of a support ticket after submission.

Important:
- Do not expose admin data.
- Do not expose internal notes.
- Do not expose internalStatus.
- Do not expose Linear, Sentry, GitHub, Replit, stack traces, provider errors, or developer handoff text.
- Do not expose other users’ tickets.
- Do not build full login/auth yet unless existing patterns already exist.
- Use a simple secure verification flow for now.
- Do not add WhatsApp OTP automation yet.

Routes:
1. /help/track-ticket
2. /help/ticket/:ticketReference

Public route 1:
Create /help/track-ticket

Purpose:
Allow a user to find a ticket by reference.

Page title:
Track Your Support Ticket

Intro text:
“Enter your ticket reference and contact email or WhatsApp number to view the latest public status.”

Fields:
- ticketReference required
- contactEmail optional
- contactWhatsapp optional

Validation:
- ticketReference required
- either contactEmail or contactWhatsapp required

Behavior:
- on submit call backend verification endpoint
- if matched, navigate to /help/ticket/:ticketReference with a short-lived access token or safe query token
- if not matched, show:
“We could not verify this ticket. Please check your reference and contact details.”

Public route 2:
Create /help/ticket/:ticketReference

Purpose:
Show a public-safe ticket detail view.

Access:
- must require a verified access token/query token/session from /help/track-ticket
- if no valid access, show a verification panel requiring email/WhatsApp matching
- do not allow public ticket viewing by reference alone

Backend:

1. POST /api/support/public/verify-ticket

Input:
- ticketReference required
- contactEmail optional
- contactWhatsapp optional

Behavior:
- find ticket scoped to Eride Technologies organisation
- match ticketReference exactly, case-insensitive if possible
- verify contactEmail matches reporterEmail OR contactWhatsapp matches reporterWhatsapp
- if matched, return:
  - success true
  - ticketReference
  - accessToken or signed token valid for short period
- if not matched, return 404 or success false without revealing whether ticket exists

Token:
- implement simple signed token using existing server secret if available
- if no existing secret, use SUPPORT_PUBLIC_TICKET_SECRET env
- fallback to a dev-only secret with clear warning in code/replit.md
- token should include ticketId and expiry
- expiry: 30 minutes

2. GET /api/support/public/tickets/:ticketReference

Requires:
- valid token

Return only public-safe fields:
- ticketReference
- productName
- productCode
- publicStatus
- category
- priority maybe omit or expose only if safe
- issueSummary
- pageOrStep
- createdAt
- updatedAt
- resolvedAt
- closedAt

Do not return:
- internalStatus
- internal notes
- status history
- Linear links
- Sentry links
- provider errors
- developer handoff
- assigned developer IDs
- raw attachments from admin unless uploaded by public user and safe

3. GET /api/support/public/tickets/:ticketReference/messages

Requires:
- valid token

Return only public-safe messages:
- direction
- channel
- messageType
- messageBody
- createdAt

Filter rules:
- include outbound messages sent to the user through email, whatsapp, in_app, manual
- include inbound user replies if they were recorded as user-facing
- exclude internal messages
- exclude internal_note channel
- exclude providerMessageId
- exclude errorMessage
- exclude internal status references

4. POST /api/support/public/tickets/:ticketReference/reply

Requires:
- valid token

Input:
- messageBody required
- uploadedByName optional

Behavior:
- create support_ticket_messages row:
  direction = inbound
  channel = in_app
  messageType = user_reply
  deliveryStatus = received
  senderName = ticket.reporterName
  recipientName = Eride Support
  messageBody = input messageBody
  relatedPublicStatus = current publicStatus
  relatedInternalStatus = current internalStatus
- do not expose relatedInternalStatus publicly in response
- optionally set internalStatus = support_review if ticket was waiting for user info
- record status history if status changes

5. Public attachment upload:
Either reuse existing attachment endpoint with token support or create:
POST /api/support/public/tickets/:ticketReference/attachments

Requires:
- valid token

Behavior:
- allow user to upload more screenshots/evidence
- use same file validation rules from Step 5
- attach file to ticket
- uploadedByName = ticket.reporterName
- uploadedByEmail = ticket.reporterEmail
- uploadedByRole = public_user

Display:

publicStatus = under_review

if ticket was closed/resolved/fixed.
